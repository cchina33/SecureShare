# SecureShare アーキテクチャ設計書

本ドキュメントでは、SecureShareのセキュリティモデル、ゼロナレッジ暗号化の仕組み、およびシステム全体のアーキテクチャ（テキスト共有および暗号化画像共有）について解説します。

---

## 1. コア設計思想：ゼロナレッジ（Zero-Knowledge）

SecureShareは、**「サーバー管理者にすら機密データの内容を閲覧できない」** ゼロナレッジ設計を徹底しています。

- **端末内暗号化**: メモ、パスワード、および画像ファイルの暗号化・復号は、すべてユーザーのブラウザ（クライアント端末）上で完結します。
- **URLハッシュによる鍵共有**: 暗号鍵は受取用URLのハッシュフラグメント（`#<Base64Key>`）に格納されます。
- **HTTP仕様による保証**: RFC 3986およびHTTPの仕様上、URLの `#` 以降（ハッシュ）は**ブラウザからサーバーへのHTTPリクエストに含まれず、サーバーに送信されません**。これにより、Cloudflareのアクセスログ、Workersの実行メモリ、ストレージのいずれにも暗号鍵が一切残りません。

---

## 2. ハイブリッドストレージ・アーキテクチャ

テキスト共有と画像共有の特性に合わせて、Cloudflare の分散インフラを適材適所で組み合わせたハイブリッド設計を採用しています。

```
                    ┌─────────────────────────┐
                    │  送信者 / 受信者ブラウザ │
                    └────────────┬────────────┘
                                 │
           ┌─────────────────────┴─────────────────────┐
           │ (HTTPS / Pages Functions API エンドポイント) │
           ▼                                           ▼
┌──────────────────────┐                    ┌──────────────────────┐
│    Cloudflare D1     │                    │    Cloudflare R2     │
│ (エッジ分散SQL DB)   │                    │ (オブジェクトストレージ) │
├──────────────────────┤                    ├──────────────────────┤
│ ・テキスト暗号文     │                    │ ・暗号化画像バイナリ │
│ ・画像メタデータ     │                    │   (最大 10MB)        │
│   (IV, MIME, 有効期限)│                    │                      │
└──────────────────────┘                    └──────────────────────┘
```

1. **Cloudflare D1 (データベース)**:
   - テキスト暗号文（`secrets` テーブル）
   - 画像メタデータ（`images` テーブル: `id`, `iv`, `mime_type`, `file_size`, `created_at`, `expires_at`, `burn_after_read`）
   - 高速なインデックス検索（`idx_secrets_expires_at`, `idx_images_expires_at`）により、有効期限判定やクリーンアップをミリ秒単位で処理。
2. **Cloudflare R2 (オブジェクトストレージ)**:
   - 大容量の暗号化画像バイナリ（`secureshare-images` バケット）を保管。
   - Egress（下り転送）料金が完全無料であるため、帯域コストを気にせずセキュアに画像を配信可能。

## 3. 暗号化・共有フロー

### A. テキスト共有フロー
```
【送信者】
 1. パスワード/メモを入力
 2. Web Crypto API で 256bit 暗号鍵をランダム生成 (AES-GCM)
 3. 平文テキストを暗号化 (暗号文 + IV を生成)
 4. POST /api/secret へ送信 ──> D1 に保管
 5. 受取URL発行: https://<domain>/view.html?id=<UUID>[&burn=0]#<Base64暗号鍵>

【受信者】
 1. 共有URLを開き、ハッシュから暗号鍵を抽出
 2. GET /api/secret/<UUID> より暗号文を取得
 3. [サーバー] ワンタイム時は即座に D1 から DELETE (物理削除)
 4. [ブラウザ] 抽出した鍵でブラウザ内で平文に復号・表示
```

### B. 画像共有フロー (Phase 1〜3 で実装)
```
【送信者】
 1. 画像ファイル (PNG, JPEG, WebP, GIF、最大10MB) を選択
 2. Web Crypto API で 256bit 暗号鍵をランダム生成 (AES-GCM)
 3. 画像の ArrayBuffer を直接バイナリ暗号化 (暗号化バイナリ + IV を生成)
    ※ Base64化を挟まないことでメモリ消費を抑え、転送量を約33%削減
 4. POST /api/image へ multipart/form-data で送信
    - 暗号化バイナリ ──> R2 バケットへ put
    - メタデータ (IV, MIME, 有効期限, 消去モード) ──> D1 images テーブルへ insert
 5. 受取URL発行: https://<domain>/view.html?id=<UUID>&type=image[&burn=0]#<Base64暗号鍵>

【受信者】
 1. 共有URLを開き、ハッシュから暗号鍵を抽出
 2. GET /api/image/<UUID> より暗号化バイナリおよびメタデータヘッダーを取得
 3. [サーバー] ワンタイム時は即座に D1 レコード削除 ＋ R2 オブジェクト削除（二重物理破棄）
 4. [ブラウザ] 暗号鍵でバイナリ復号 ──> Blob URL 生成 ──> プレビュー表示・安全なダウンロード
```

## 4. 暗号化技術仕様

| 項目 | 採用技術 | 説明 |
|---|---|---|
| **暗号化アルゴリズム** | AES-GCM (Galois/Counter Mode) | 高速かつ認証付き暗号 (AEAD) による改ざん検知耐性を備えた共通鍵暗号 |
| **鍵長** | 256 bit | 量子コンピュータ脅威前において業界最高峰の堅牢度 |
| **初期化ベクトル (IV)** | 12 byte (96 bit) | 操作ごとに `crypto.getRandomValues()` で衝突不可能な暗号学的擬似乱数を生成 |
| **暗号化エンジン** | Web Crypto API (`window.crypto.subtle`) | OS・ブラウザ標準のネイティブC++実装（外部JSライブラリ不要で極めて安全かつ高速） |
| **画像暗号化方式** | `ArrayBuffer` 直接バイナリ暗号化 | 巨大なBase64文字列への変換を行わず、生のバイナリストリームとして効率的に処理 |

## 5. 消去モードと二重の保護ライフサイクル

### 2つの消去モード
| モード | 動作仕様 | ユースケース |
|---|---|---|
| **⚡ 閲覧後に即時消去 (ワンタイム)** | 受信者が一度表示すると、D1およびR2から**直ちに完全物理削除**。2回目のアクセスは404。 | パスワード、機密画像、身分証コピー、APIキー |
| **⏳ 期限まで保持** | 指定した有効期限が切れるまで、同じURLから**何度でも再閲覧可能**。 | 複数人での共有、後から見返したいマニュアルや画像 |

### 有効期限ポリシーと二重のセーフティネット
- **テキスト共有**: 最短1時間 〜 **最長30日間**
- **画像共有**: 最短1時間 〜 **最長8日間**（容量肥大化と放置防止の厳格ポリシー）
- **R2 ライフサイクルルール (フェイルセーフ)**:
  - バケット `secureshare-images` に対し、**作成から9日後に無条件自動削除（`auto-delete-9days`）** を設定。
  - Cronワーカーやアプリ側の削除処理が停止した場合でも、Cloudflare のストレージ基盤レベルでデータが永久に残ることを確実に防ぎます。

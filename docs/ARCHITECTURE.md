# SecureShare アーキテクチャ設計書

本ドキュメントでは、SecureShareのセキュリティモデル、ゼロナレッジ暗号化の仕組み、およびシステム全体のアーキテクチャについて解説します。

---

## 1. コア設計思想：ゼロナレッジ（Zero-Knowledge）

SecureShareは、**「サーバー管理者にすら機密データの内容を閲覧できない」** ゼロナレッジ設計を徹底しています。

- **端末内暗号化**: メモやパスワードの暗号化・復号は、すべてユーザーのブラウザ（クライアント端末）上で完結します。
- **URLハッシュによる鍵共有**: 暗号鍵は受取用URLのハッシュフラグメント（`#<Base64Key>`）に格納されます。
- **HTTP仕様による保証**: RFC 3986およびHTTPの仕様上、URLの `#` 以降（ハッシュ）は**ブラウザからサーバーへのHTTPリクエストに含まれず、サーバーに送信されません**。これにより、CloudflareのアクセスログやWorkersの処理メモリにも暗号鍵が一切残りません。

---

## 2. 暗号化・共有フロー

```
【送信者 (ブラウザ)】
 1. パスワードまたは秘密メモを入力
 2. Web Crypto API で 256bit 暗号鍵をランダム生成 (AES-GCM)
 3. 暗号化を実行 (暗号文 + IV を生成)
 4. POST /api/secret へ「暗号文」「IV」「有効期限」「Turnstileトークン」を送信
    ※ 暗号鍵は絶対にサーバーへ送信しない
 5. 発行されたIDと暗号鍵から受取用URLを構築:
    https://<domain>/view.html?id=<UUID>[&burn=0]#<Base64暗号鍵>

【受信者 (ブラウザ)】
 1. 共有URLを開く
 2. ブラウザがURLのパスからID、ハッシュから暗号鍵を抽出
 3. GET /api/secret/<UUID> より暗号文とIVを取得
 4. [サーバー側] 
    - ワンタイムモード: 取得直後にD1データベースから該当レコードを即座に DELETE (物理削除)
    - 期限保持モード: 削除せずレコードを維持 (有効期限が切れるまで何度でも閲覧可能)
 5. [ブラウザ側] 抽出した暗号鍵を用いてブラウザ内で平文に復号・表示
```

---

## 3. 暗号化技術仕様

| 項目 | 採用技術 | 説明 |
|---|---|---|
| **暗号化アルゴリズム** | AES-GCM (Galois/Counter Mode) | 高速かつ認証付き暗号 (AEAD) による改ざん耐性を備えた共通鍵暗号 |
| **鍵長** | 256 bit | 現在の標準暗号解読技術に対して極めて堅牢な強度 |
| **初期化ベクトル (IV)** | 12 byte (96 bit) | メッセージごとに `crypto.getRandomValues()` で安全に乱数生成 |
| **暗号化エンジン** | Web Crypto API (`window.crypto.subtle`) | ブラウザ標準のネイティブ実装（外部ライブラリ非依存・高速） |

---

## 4. 2つの消去モード

| モード | 動作仕様 | ユースケース |
|---|---|---|
| **⚡ 閲覧後に即時消去 (ワンタイム)** | 受信者が一度シークレットを表示すると、D1から直ちに完全物理削除。2回目のアクセスは404。 | パスワード、APIキー、機密個人情報の単発共有 |
| **⏳ 期限まで保持** | 指定した有効期限（1時間〜最長30日）が切れるまで、同じURLから何度でもアクセス可能。 | 複数人への資料共有、受取側が後から見返すメモ |

※ どちらのモードであっても、有効期限を過ぎたデータはCloudflare Scheduled Cron Workerによって定期的に一括自動削除されます。
